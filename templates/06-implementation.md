## 6.0 核心原则：Boil the Lake（煮沸湖泊）

> **AI 辅助编程让完整实现的边际成本接近于零**

### 湖泊 vs 海洋

| 类型 | 定义 | 策略 |
|------|------|------|
| **湖泊 (Lake)** | 可煮沸的：100% 测试覆盖、完整功能、所有边界情况 | ✅ **煮沸它** — 一次性做到完美 |
| **海洋 (Ocean)** | 不可煮沸的：整个系统重写、跨季度平台迁移 | ⚠️ **标记为超出范围** |

### 决策框架

面对 "方案 A（完整，~150 行）vs 方案 B（90%，~80 行）"：

```
如果 A 只比 B 多 70 行代码
→ 选择 A（70 行 = AI 辅助下几秒钟的差异）
```

### 反模式

❌ "选 B —— 它用更少的代码覆盖 90%"  
❌ "我们把测试推迟到后续 PR"  
❌ "边缘情况不太可能发生"

### 收益复利

```
100% 完成度 → 零技术债务 → 6 个月后维护成本降低 50%
90% 完成度 → 每 10 行 1 个债务点 → 持续维护成本累积
```

## 6.6 代码简化 (Simplify) - 实现后优化

> **时机**: 所有任务完成且测试通过后，提交代码前  
> **目标**: 自动化代码审查和清理，提升代码质量

### 6.6.1 变更检测

```bash
# 确定审查范围
git diff HEAD~1  # 最近提交的变更
git diff         # 未提交的变更
```

### 6.6.2 三维度并行审查

并行运行以下三个审查方向：

#### 维度 1: 代码复用 (Code Reuse)

- [ ] 检查是否有重复逻辑可提取为共享函数
- [ ] 检查是否使用了现有的工具函数而非重新实现
- [ ] 识别冗余代码块和重复模式
- [ ] 寻找重构为可复用组件的机会

**发现示例**:
```
重复代码: 第 45-50 行和第 120-125 行逻辑相同
建议: 提取为 validate_input() 函数
```

#### 维度 2: 代码质量 (Code Quality)

- [ ] 命名一致性（函数、变量、结构体命名符合项目规范）
- [ ] 函数分解（单个函数不超过 50 行，单一职责）
- [ ] 控制流清晰度（避免深层嵌套，提前返回）
- [ ] 符合 CLAUDE.md 中的编码规范
- [ ] 检查代码异味:
  - [ ] 过度工程化 / 过早优化
  - [ ] 不必要的抽象
  - [ ] "Stringly-typed" 代码（用字符串代替类型）
  - [ ] 泄漏的抽象

**发现示例**:
```
问题: process_data() 函数 120 行，处理 5 种不同逻辑
建议: 拆分为 5 个专用函数，主函数作为编排器
```

#### 维度 3: 性能优化 (Efficiency)

- [ ] 不必要的内存分配
- [ ] 冗余计算
- [ ] N+1 查询模式
- [ ] 低效的文件/网络访问
- [ ] 错失的并发机会
- [ ] 不必要的重新渲染（前端）

**发现示例**:
```
问题: 循环中多次调用相同的数据库查询
建议: 使用 JOIN 一次性获取，或缓存结果
```

### 6.6.3 修复应用

**优先级**: 高 → 中 → 低

| 优先级 | 处理策略 |
|--------|---------|
| **高** | 必须修复（安全问题、明显 bug、性能问题） |
| **中** | 建议修复（代码异味、可读性问题） |
| **低** | 可选（风格偏好、微小优化） |

## 6.7 会话上下文管理 (借鉴 Compact Service)

> **长会话时保持上下文清晰**

### 何时进行上下文压缩

| 触发条件 | 压缩范围 | 输出 |
|---------|---------|------|
| 对话 > 50 轮 | 整个会话 | 完整摘要 |
| 新增 > 20 轮 | 仅新消息 | 增量摘要 |
| 中断后恢复 | 旧消息 | 恢复摘要 |

### 压缩内容结构

```markdown
## 会话摘要 [日期] - Phase 6 实现阶段

### 主要请求
当前任务: 
实现目标: 

### 关键决策
1. 
2. 

### 文件变更
| 文件 | 变更类型 | 关键修改 |
|------|---------|---------|
| | 创建/修改/删除 | |

### 遇到的问题
| 问题 | 状态 | 解决方案 |
|------|------|---------|
| | 已解决/进行中 | |

### 当前进度
- [ ] 任务 1
- [x] 任务 2
- [ ] 任务 3 (进行中)

### 下一步
1. 
```

### 压缩策略

**完整压缩**: 整个会话 → 单个摘要文档  
**部分压缩**: 旧消息压缩 + 保留最近 10-20 轮  
**分层压缩**: 多层摘要（最新完整 → 中层摘要 → 早期概要）

## 6.8 破坏性操作检查 (借鉴 gstack /careful)

> **在以下操作前，必须确认并记录**

### 高风险操作清单

| 操作类型 | 示例 | 确认方式 | 状态 |
|---------|------|---------|------|
| **删除** | `rm -rf`, `DROP TABLE`, 删除分支 | 用户确认 + 备份已创建 | ⬜ |
| **强制推送** | `git push --force` | 确认无其他人基于此分支 | ⬜ |
| **重置** | `git reset --hard` | 确认变更已保存/提交 | ⬜ |
| **修改提交** | `git rebase`, `amend` | 确认未推送或团队协作已知 | ⬜ |
| **降级依赖** | 移除包、降级版本 | 检查依赖链影响 | ⬜ |
| **修改 CI/CD** | 变更 pipeline | 确认不影响其他分支 | ⬜ |
| **共享状态变更** | 修改共享配置、权限 | 通知团队 | ⬜ |
| **外部服务** | 发送消息、创建 PR | 确认内容和接收方 | ⬜ |

### 安全检查流程

```
1. 识别操作风险等级
   ├── 本地可逆操作 → 可继续
   ├── 本地不可逆操作 → 确认备份
   ├── 影响共享状态 → 用户确认
   └── 破坏性操作 → 二次确认 + 记录

2. 执行前确认
   - [ ] 已理解操作后果
   - [ ] 已创建备份（如需要）
   - [ ] 已通知相关人员（如需要）

3. 执行后验证
   - [ ] 操作结果符合预期
   - [ ] 无意外副作用
   - [ ] 系统状态一致
```

### 自动化保护建议

在项目 CLAUDE.md 中配置：

```markdown
## 破坏性操作保护

以下操作需要显式确认：
- rm -rf（任何目录）
- git push --force
- DROP TABLE
- 修改 main/master 分支
- 修改生产环境配置
```
