# Phase 8: Evolution & Governance（演化与治理）

> **目的**: 项目上线后，保持长期掌控力——防止架构 drift、决策失忆、复杂度膨胀
> **输入**: Phase 7 的上线产品 + 持续迭代需求
> **输出物**: 持续维护的治理文档，存放到 `<project>/docs/`
>
> ⚠️ **Phase 1-7 是"造船"，Phase 8 是"航海"。船下水后需要航海日志、维修记录和航线校正。**
> ⚠️ **本阶段不是一次性的，而是项目存续期间持续执行。**

---

## 8.1 决策日志 (Decision Log)（必填）

> **问题**: 6 个月后，你会问"为什么当初选这个数据库？""这个边界条件是谁定的？"
>
> **关键**: 不要只记"选了什么"，要记"当时为什么选"和"什么情况下会推翻"。

### 模板

在 `docs/DECISIONS.md` 中维护：

| 日期 | 决策 | 选项 | 选择 | 决策者 | 当时假设 | 若假设失效怎么办 |
|------|------|------|------|--------|---------|----------------|
| | | A / B / C | | | | |

### 示例

| 日期 | 决策 | 选项 | 选择 | 决策者 | 当时假设 | 若假设失效怎么办 |
|------|------|------|------|--------|---------|----------------|
| 2025-04 | 支付方案 | Stripe / 支付宝 | 支付宝 | @davirain | MVP 只服务国内用户 | 若出海，需抽象支付接口 |
| 2025-04 | 数据库 | PostgreSQL / Mongo | PostgreSQL | @davirain | 强关系型数据，需要 ACID | 若数据模型变文档型，评估迁移成本 |
| 2025-05 | 认证方案 | 自建 / Auth0 / Clerk | 自建 | @davirain | 简单手机号验证足够 | 若需 OAuth/SSO，迁移到 Clerk |

### 什么时候必须记录

- [ ] 选择了一个依赖/库/框架
- [ ] 选择了一种架构模式
- [ ] 决定了"不做什么"
- [ ] 推翻了之前的决策
- [ ] 做了任何"成本高于 1 天"的取舍

## 8.2 架构决策记录 ADR (Architecture Decision Records)（必填）

> **问题**: Phase 2 的架构文档写完后，随着迭代会被默默违背。ADR 让架构决策变成有约束力的契约。
>
> **与决策日志的区别**: Decision Log 是流水账（所有决策），ADR 是重大架构决策的深度记录。

### ADR 存放位置

```
docs/ADR/
├── ADR-001-payment-only-alipay.md
├── ADR-002-self-hosted-business-logic.md
├── ADR-003-postgresql-over-mongo.md
└── _template.md
```

### ADR 模板

```markdown
# ADR-NNN: [决策标题]

## 状态
[Proposed / Accepted / Deprecated / Superseded by ADR-XXX]

## 背景
为什么需要做这个决策？当时的约束和上下文是什么？

## 决策
具体选择了什么方案？

## 后果
- ✅ 正面影响：
- ❌ 负面影响：
- ⚠️ 需要注意的约束：

## 约束（机械强制）
什么规则必须遵守？违反时的检测机制是什么？
例：任何引入新支付渠道的 PR，必须触发 ADR 复审。

## 推翻条件
什么情况下应该重新审视这个决策？
```

### ADR 生命周期

```
Proposed → 讨论 → Accepted → [长期有效]
                              ↓
                         Deprecated（假设失效）
                              ↓
                     Superseded by ADR-XXX（被新决策替代）
```

**规则**: 任何人想打破已 Accepted 的 ADR，必须明确说"我要推翻 ADR-NNN"，并走新的 ADR 流程。

## 8.3 复杂度预算 (Complexity Budget)（推荐）

> **问题**: 大项目的崩溃不是一个大错误，而是"每个小功能都加 5% 复杂度"，直到无人能懂。
>
> **使用时机**: 项目达到 5+ 模块时启用。

### 预算表

| 模块 | 复杂度评分 (0-30) | 上限 | 理由 | 上次评估 |
|------|-------------------|------|------|---------|
| | | | | |

**总预算**: ___ 点  
**已使用**: ___ 点  
**剩余**: ___ 点

### 复杂度评分标准

| 分值 | 含义 | 特征 |
|------|------|------|
| 1-5 | 简单 | 纯 CRUD，单一职责，无跨模块依赖 |
| 6-10 | 中等 | 有状态管理，2-3 个依赖 |
| 11-20 | 复杂 | 状态机、并发逻辑、跨模块事务 |
| 21-30 | 高复杂 | 分布式状态、复杂权限、多方交互 |

### 规则

- 新增功能若使某模块复杂度 **+3 以上**，必须先做减法或拆分模块
- 每个 Milestone 结束时重新评估各模块复杂度
- 总复杂度超出预算时，必须先还债再加功能

### 减法清单

当复杂度超出预算时，按优先级做减法：

| 优先级 | 减法方式 | 预期效果 |
|--------|---------|---------|
| 1 | 删除未使用的代码/功能 | 直接减少 |
| 2 | 合并重复模块 | 减少维护面 |
| 3 | 抽象共同模式 | 降低认知负担 |
| 4 | 拆分过大模块 | 降低单点复杂度 |
| 5 | 降级功能（简化而非删除） | 在保留价值的前提下降复杂度 |

## 8.4 交接地图 (Onboarding Map)（必填）

> **问题**: 项目变大后，新 AI 会话或新人需要很长时间才能理解结构。而这段时间足以让 AI 写出大量偏离方向的代码。
>
> **目标**: 10 分钟读完就能定位到相关代码。

### 模板

在 `docs/ONBOARDING.md` 中维护：

```markdown
# 10 分钟 Onboarding

## 项目一句话
[项目是什么，用一句话说清]

## 绝对不能碰的边界（对齐锚点摘要）
1. [从 Phase 1 的对齐锚点中提取最重要的 3 条]
2. 
3. 

## 代码地图
| 目录 | 职责 | 对应规格 | 负责人 |
|------|------|---------|--------|
| | | `03-technical-spec.md#xxx` | |

## 最近 3 个重要决策
见 `DECISIONS.md` 最新 3 条。

## 如果你要改 __，先看 __
| 要改的区域 | 必须先读 | 必须先问的人 |
|-----------|---------|-------------|
| | | |

## 当前系统状态
- 最新版本：
- 活跃分支：
- 已知问题：见 `docs/07-review-report.md` 已知问题节
```

### 更新频率

- 每次架构变更后同步
- 每次 ADR 新增或废弃后更新"如果你要改 __，先看 __"
- 每个 Milestone 结束时检查是否过期

### 关键原则

- **不要写"项目是怎么发展起来的"** → 写"你现在要从哪开始"
- **不要复制技术规格** → 只写定位信息和交叉引用
- **新 AI 会话的第一个 prompt 应该是"读 ONBOARDING.md"**

## 8.5 运行态对齐 (Runtime Alignment)（可选，有真实用户后启用）

> **问题**: 代码完全符合 Phase 3 规格，但系统行为可能偏离设计意图（用户不按你设想的路径走）。
>
> 这是防止"代码对了，产品错了"的最后一道防线。

### 运行态对齐检查表

每双周（或每月）一次：

| 设计意图 | 监控指标 | 实际数据 | 偏差？ | 行动 |
|---------|---------|---------|--------|------|
| | | | ✅/⚠️/🔴 | |

### 示例

| 设计意图 | 监控指标 | 实际数据 | 偏差？ | 行动 |
|---------|---------|---------|--------|------|
| 用户 3 步完成下单 | 漏斗转化率 | 12% 完成 | ⚠️ 高流失 | 调查第 2 步流失原因 |
| AI 只处理 20% 咨询 | AI 介入率 | 67% | 🔴 严重偏离 | 业务逻辑可能太弱 |
| 订单 5 秒内同步 | P95 同步延迟 | 4.2s | ✅ 正常 | — |
| 日活跃用户 100+ | DAU | 23 | ⚠️ 低于预期 | 回顾获客策略 |

### 偏差处理流程

```
🟢 正常 → 继续
⚠️ 偏离 → 记录到 Drift Log，安排调查
🔴 严重偏离 → 立即暂停相关功能迭代，优先修复
```

## 8.6 治理节奏总结

| 频率 | 活动 | 输出 |
|------|------|------|
| **每次重大决策时** | 记录 Decision Log + ADR（如适用） | DECISIONS.md, docs/ADR/ |
| **每次架构变更后** | 更新 Onboarding Map | ONBOARDING.md |
| **每个 Milestone** | 复杂度预算重评估 + 代码库熵检查 | 本文档更新 |
| **每双周（有用户后）** | 运行态对齐检查 | 运行态对齐表 |
| **每月** | 回顾 Drift Log + ADR 有效性 | 标记过期 ADR |

## ✅ Phase 8 验收标准（持续性）

Phase 8 没有"完成"的概念，而是持续验收：

- [ ] Decision Log 在每次重大决策后 24 小时内更新
- [ ] 重大架构决策有对应 ADR
- [ ] Onboarding Map 能让新 AI 会话在 10 分钟内理解项目
- [ ] 复杂度预算在每个 Milestone 后重评估（5+ 模块时）
- [ ] 无过期或被默默违背的 ADR
