# 附录：摩擦检查清单 (Friction Checklist)

> 借鉴 Armin Ronacher "The Friction Is Your Judgment" (AI Engineer 2026 伦敦)
> 摩擦不是敌人。摩擦就是你的判断力。

---

## F.1 心理学自检 (Psychology Check)

> **使用时机**: 每周一次，或当你感觉"产出很多但不确定方向对不对"时。
>
> 目标：识别速度陷阱和责任转移，在失控之前修正。

### 速度陷阱诊断

| 问题 | 诚实回答 | 信号 |
|------|---------|------|
| 我现在是在**推进**还是在**追求发布的快感**？ | | 如果分不清，你已经在陷阱里了 |
| 过去一周我跳过了几次"等一下，让我想想"？ | | > 3 次 = 黄灯 |
| 我最近一次说"不，这个方向不对"是什么时候？ | | > 1 周前 = 黄灯 |
| 我是否因为代理产出很快，就接受了一个我不完全理解的方案？ | | 任何一次 = 红灯 |
| 我能在不看代码的情况下，向别人解释系统的整体架构吗？ | | 不能 = 红灯 |

### 责任转移诊断

| 问题 | 诚实回答 | 信号 |
|------|---------|------|
| 我最近审查 PR 时，是在**真正审查**还是在**橡皮图章**？ | | 审查时间 < 5 分钟 = 橡皮图章 |
| 我是否用"小 PR"策略来减少审查负担，而非真正降低复杂度？ | | |
| 出了问题我的第一反应是"代理搞的"还是"我的判断失误"？ | | 前者 = 你在转移责任 |
| 我是否在让代理做我自己还没想清楚的事？ | | 代理不能替你思考 |

### 自检结果

```
日期: ____
状态: 🟢 健康 / 🟡 需要注意 / 🔴 立即停下来

如果 🟡 或 🔴:
- 停止产出，花 30 分钟审视方向
- 回顾最近 3 天的 commit，问自己：哪些是真正的进步？哪些只是产出？
- 如果不确定，找一个同事解释你在做什么。如果解释不清楚，你已经失控了。
```

## F.2 代码库健康度自检 (Codebase Health Check)

> **使用时机**: 每个 Milestone 完成后，或感觉"代理产出的代码越来越奇怪"时。
>
> 目标：在熵的正反馈循环（越乱 → 代理越差 → 越乱）吞噬代码库之前，中断它。

### 熵指标

| 检查项 | 状态 | 健康标准 |
|--------|------|---------|
| **我能解释每个模块的职责吗？** | ✅/❌ | 每个模块一句话可描述 |
| **函数命名是否一致？** | ✅/❌ | 同类操作使用统一动词（get/fetch/retrieve 不混用） |
| **错误处理模式是否统一？** | ✅/❌ | 全项目同一种错误传播策略 |
| **是否存在重复代码？** | ✅/❌ | 相同逻辑不超过 2 处 |
| **代理最近产出的代码是否有 bare catch？** | ✅/❌ | 零 bare catch-all |
| **是否有"我不确定这段代码为什么在这里"的模块？** | ✅/❌ | 零个这样的模块 |
| **新加入的人（或新的代理会话）能快速理解项目吗？** | ✅/❌ | 仅靠文档和代码结构即可理解 |

### 熵趋势判断

```
上次检查: ____
本次检查: ____

趋势: 📈 熵在增加 / ➡️ 稳定 / 📉 熵在减少

如果 📈:
- 停止新功能开发
- 进行一轮代码清理（Phase 6.6 Simplify）
- 加强机械强制规则（Phase 2.7 Agent Guardrails）
- 清理后重新评估
```

## F.3 机械强制规则清单 (Mechanical Enforcement)

> **使用时机**: 项目启动时（Phase 2）定义，持续维护。
>
> 核心思想：不要依赖代理或人类的自律，通过工具链把护栏硬编码进流程。

### 通用规则（所有项目）

| 规则 | 为什么 | 强制方式 |
|------|--------|---------|
| 禁止裸 catch-all 异常处理 | 失败应向上传播，静默吞噬错误是最危险的反模式 | Linter 规则 |
| 禁止提交含敏感信息的文件 | .env、credentials 不应进入仓库 | pre-commit hook + .gitignore |
| 测试覆盖率不得低于门槛 | 防止质量无感知地滑坡 | CI gate |
| 所有公共 API 变更必须有对应测试 | 防止行为无意中改变 | CI gate |

### JavaScript / TypeScript 项目

| 规则 | ESLint 规则 | 说明 |
|------|------------|------|
| 禁止 `any` 类型 | `@typescript-eslint/no-explicit-any` | 类型安全是代理可读性的基础 |
| 禁止 `console.log`（生产代码） | `no-console` | 使用结构化日志 |
| 禁止 dynamic imports（如适用） | `import/no-dynamic-require` | 防止运行时不可预测依赖 |
| UI 禁止 raw `<input>`（如使用组件库） | 自定义规则 | 必须使用设计系统组件 |
| 启用 `erasableSyntaxOnly`（TypeScript） | tsconfig | 限制不安全的 TS 模式 |

### Rust 项目

| 规则 | Clippy lint | 说明 |
|------|------------|------|
| 禁止 `unwrap()` | `clippy::unwrap_used` | 使用 `?` 或显式错误处理 |
| 禁止 `expect()` 在库代码中 | `clippy::expect_used` | 库不应 panic |
| 禁止 `unsafe` 无注释 | `clippy::undocumented_unsafe_blocks` | 所有 unsafe 必须解释 |

### Python 项目

| 规则 | 工具 | 说明 |
|------|------|------|
| 禁止 bare `except:` | Ruff `E722` | 必须指定异常类型 |
| 类型注解覆盖 | mypy strict mode | 公共 API 必须有类型注解 |
| 禁止 `import *` | Ruff `F403` | 显式导入，避免命名空间污染 |

### 自定义规则模板

根据项目需求补充：

|------|---------|--------|------|
| | | | ⬜ 待实施 / ✅ 已实施 |
| | | | |

## F.4 审查分工矩阵 (Review Responsibility Matrix)

> 快速查表：这个变更应该谁来审查？

| 变更类型 | 审查者 | 审查深度 | 阻塞合并？ |
|---------|--------|---------|-----------|
| 代码格式 / 样式 | 🤖 代理（CI） | 自动 | 是（自动修复） |
| 未使用变量 / 死代码 | 🤖 代理（Linter） | 自动 | 是 |
| 测试覆盖率下降 | 🤖 代理（Coverage） | 自动报告 | 是（低于门槛时） |
| 依赖安全漏洞 | 🤖 代理（Audit） | 自动扫描 | Critical 时阻塞 |
| 类型检查错误 | 🤖 代理（tsc/mypy） | 自动 | 是 |
| **数据库 Schema 变更** | 🧠 **人类** | 逐行 | **是** |
| **新依赖引入** | 🧠 **人类** | 评估必要性和风险 | **是** |
| **认证/授权逻辑** | 🧠 **人类** | 安全审查 | **是** |
| **破坏性 API 变更** | 🧠 **人类** | 影响评估 | **是** |
| **不可逆操作（删除/迁移）** | 🧠 **人类** | 二次确认 | **是** |
| **架构/设计变更** | 🧠 **人类** | 全局一致性 | **是** |
| 新功能实现 | 🧠 人类 + 🤖 代理 | 人类审设计，代理审机械 | 是 |
| Bug 修复 | 🧠 人类 + 🤖 代理 | 人类审根因，代理审回归 | 是 |

## F.5 定期复盘问题 (Friction Retro)

> 每个 Milestone 结束或每两周一次，花 15 分钟回答以下问题。

1. **这个周期中，我们"跳过思考"的次数是多少？** 列出具体事例。
2. **有没有代理产出的代码在合入后才发现问题？** 根因是什么——审查不足、规格不清、还是代码库熵太高？
3. **机械强制规则拦住了什么？** 如果什么都没拦住，要么规则不够，要么代理已经很好地遵守了。
4. **哪些地方本应加摩擦但没加？** 这些地方加上去。
5. **哪些地方的摩擦是纯浪费？** 这些地方减掉或自动化。
6. **代码库健康度相比上次检查是好转还是恶化？**

---

*没有摩擦，你就无法掌控方向。定期自检，让摩擦成为你的方向盘而非障碍。*
