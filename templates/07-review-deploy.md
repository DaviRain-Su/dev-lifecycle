# Phase 7: Review & Deploy（审查与部署）

> **目的**: 确保代码质量和安全性，部署到目标环境
> **输入**: Phase 6 的代码 + 测试结果
> **输出物**: 审查报告 + 部署记录，存放到 `<project>/docs/07-review-report.md`

## 7.1 代码审查（必填）

### 7.1.1 自审清单

- [ ] 代码与技术规格 100% 一致
- [ ] 所有公开接口有文档注释
- [ ] 无硬编码的密钥/密码/敏感信息

- [ ] 日志/事件适当（可观测性）

### 7.1.2 对抗性验证 (Verification Agent)

> **目标**: 不是确认实现有效，而是尝试**打破它**。
> 
> **原则**: 前 80% 的实现是容易的，价值在于发现最后 20% 的问题。

#### 验证策略（按变更类型）

| 变更类型 | 验证步骤 | 预期输出 |
|---------|---------|---------|
| **前端** | 1. 启动 dev server<br>2. 浏览器自动化测试（点击、截图、控制台）<br>3. curl 子资源（JS/CSS/图片） | 页面渲染正常，交互可用，资源加载成功 |
| **后端/API** | 1. 启动 server<br>2. curl/Fetch 端点<br>3. 验证响应结构<br>4. 测试错误处理 | 响应符合规格，错误码正确，边界情况处理 |
| **CLI/脚本** | 1. 运行代表性输入<br>2. 验证 stdout/stderr/exit codes<br>3. 测试边缘输入（空、异常、边界） | 输出正确，退出码合理，边缘输入不崩溃 |
| **基础设施** | 1. 语法验证<br>2. dry-run（如 terraform plan）<br>3. 检查 env vars 引用 | 语法正确，dry-run 无错误，变量已定义 |
| **库/包** | 1. 构建<br>2. 完整测试套件<br>3. 从新鲜上下文导入并测试 API | 构建成功，测试通过，API 行为符合文档 |
| **Bug 修复** | 1. 复现原 bug<br>2. 验证修复<br>3. 回归测试 | 原 bug 不再复现，无引入新问题 |
| **数据库迁移** | 1. 运行 migration up<br>2. 验证 schema<br>3. 运行 migration down | Schema 正确，可回滚，现有数据无损 |
| **重构** | 1. 现有测试套件必须通过<br>2. diff 公共 API 表面<br>3. 验证行为一致 | 测试通过，API 无变化，输入输出一致 |

#### 必须执行的基线检查

- [ ] 阅读项目 CLAUDE.md / README 了解构建/测试命令
- [ ] 运行构建（如适用）— 构建失败 = 自动 FAIL
- [ ] 运行项目测试套件 — 测试失败 = 自动 FAIL
- [ ] 运行 linter/type-checker（eslint, tsc, mypy 等）
- [ ] 检查相关代码的回归

#### 禁止的验证逃避模式

❌ **"代码看起来正确基于我的阅读"** → 必须运行验证，阅读 ≠ 验证  
❌ **"实现者的测试已通过"** → 必须独立验证，实现者也是 AI  
❌ **"这可能没问题"** → 必须确认，可能 ≠ 验证  
❌ **"让我启动 server 检查代码"** → 必须实际调用端点测试

**安全边界检查**

**允许的安全活动** ✅

#### 置信度校准

每个发现必须包含置信度评分 (1-10):

| 分数 | 含义 | 显示规则 |
|------|------|---------|
| 9-10 | 已验证具体代码，明确 bug | 正常显示 |
| 7-8 | 高置信度模式匹配 | 正常显示 |
| 5-6 | 中等，可能有误报 | 显示并提示验证 |
| 3-4 | 低置信度 | 仅附录 |
| 1-2 | 猜测 | 仅 P0 时报告 |

**发现格式**:
```
[严重度] (confidence: N/10) file:line — 描述
```

示例:
- `[P1] (confidence: 9/10) app/models/user.rb:42 — SQL injection via string interpolation`
- `[P2] (confidence: 5/10) app/controllers/api.rb:18 — Possible N+1 query, verify with logs`
